# 全文一致性与能力范围审稿

适用于不同类型 GitHub 仓库的正式文档，包括 README、用户指南、接口说明、开发和维护手册、版本记录。不是每个项目都需要这些文档；按读者任务选择相关检查。本表是交付前的核对步骤，不是长期保存的额外审稿报告。结论应有可核实的依据；源码中存在某段实现，不代表面向所有使用者提供了同名能力。

## 第一轮：声明清单（修改前后对照）

按文档主题抽取对读者有影响的关键断言，而不是逐句抄录。以下维度只在相关时填写，不能为了填满表格强行引入新概念：

| 维度 | 核对内容 |
| --- | --- |
| 事项与主体 | 什么功能、约束、操作或契约；由谁提供、对谁生效 |
| 适用范围 | 相关产品或模块、版本、平台、环境、用户角色、接口或部署形态；不相关的维度不写 |
| 可用状态 | 目标读者当前可用、内部存在但未开放、仅实验验证、明确不支持；仅在需要区分时列出 |
| 前置条件 | 依赖、输入、权限、配置或执行顺序 |
| 行为与边界 | 成功后的可观察结果、失败条件、限制及数据保留承诺 |
| 核实依据与位置 | 代码/测试/权威资料；在何处完整说明、何处引用 |

对比改写前后的**否定词、量词、数字、时间、权限、平台、代码标识符、操作命令、链接**。把一句改长但没有增加可靠信息，也不算提升。

## 第二轮：横向冲突

从同一事项出发横跨相关章节和文档查找：概览与限制、安装与实际命令、接口与使用说明、部署与运行前提、不同语言版本。注意「支持」「不能」「不会」「仅」「默认」「自动」「可选」「需要」等词各自限定的对象和场景。

### 示例：局部成立的事实不能写成全局承诺

以下是**假设性示例**，不对应任何真实项目：

- 「接口支持批量导出」限定了某个接口的行为。
- 「命令行工具目前只能单条导出」限定了另一个使用入口。
- 「导出操作需要管理员权限」限定了执行条件。

这三条可以同时成立。如果 README 只写「支持批量导出」，读者可能误以为所有入口都支持；如果一律写成「不支持批量导出」，又会掩盖接口能力。应核实主体、条件和适用范围，再给出准确表述。

同类问题也可能出现在平台差异、依赖版本、权限角色、功能开关、实验能力与稳定能力之间。不要把这些维度写成每个仓库必须具备的清单。

### 示例：语义数量一致不等于事实一致

两个语言版本的标题和条目数一致，仍可能一个写「适用于两个平台」，另一个只写「适用于一个平台」。仅靠标题/条目计数不能判断事实一致；逐项核对关键断言、前置条件、否定语义、数值和命令。

## 第三轮：最终成稿复核

1. **从头读成稿**，不要只看 Diff 的新增行。功能、步骤、已知限制是否互相支持，有无互相否定或缺少限定范围的断言。
2. 对照修改前有效事实与当前实现：确保没有丢失安装条件、关键链接、权限边界、错误处理、数据保留/回滚承诺。
3. 检查是否把多处定义同一契约；只保留一个权威说明，其他位置给简短索引或链接。不要删掉跨章节查找时必须出现的关键限制提示。
4. 让 `myshuohua` 检查**最终成稿**的用语、句法、术语和重复；修正内容后再读所触及的段落，确认没有新歧义。
5. 运行 `lint-docs.mjs`、需要时运行相关测试；保留没有解决的告警和事实冲突，不把「lint 没报」当成通过。

**失败处理**：发现互相矛盾但无法核证的声明，或新稿改变了无证据支持的产品承诺时，停止将其宣称为完成，向维护者提供文件位置、冲突的两条说法及需要核实的事实。不要因审稿扩大当前授权范围。
