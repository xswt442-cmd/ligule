# Agent guide

`ligule` is an agent harness under development. The 0.0.x line is a placeholder: the repository, the npm package name and the license are claimed, the behaviour is not settled yet.

## Engineering

- Keep `package.json#version` and `src/index.js#VERSION` equal; `test/kernel.test.js` asserts it.
- The kernel imports no transport, no UI framework and no adapter. CLI and desktop are adapters over the same interface, and adding one must not change a line of the kernel.
- `src/` is divided by layer: `kernel/` holds the tool table, decision chain, loop, prompt assembly, slot registry, assembly list, mode loader, result shapes, config, log and error codes; `capability/` holds path boundaries, probing, command parsing and execution, the search and trash backends, network target classification, instruction loading and limits; `tools/` holds the read-only three, the four write tools, the first-party optional tools, what they share and the minimal list; then `session/`, `model/`, `host/` and `tui/`. Dependencies point toward `kernel/`, never the other way, and `test/architecture.test.js` scans those directories instead of a hand-written file list, so a new file is covered without anyone remembering to add it. Platform-specific code belongs in `capability/` (D18).
- `src/` is the source and `dist/` is what `npm run build` writes (`tsc`, D47): `bin`, `exports` and `files` point at `dist/`, and the tests import `dist/` too, so a green `npm test` exercised the bytes that ship. The build runs with `allowJs` and `checkJs: false` — new modules are TypeScript under `strict` with only erasable syntax (no `enum`, no `namespace`, no parameter properties), the older JavaScript files are copied through and convert layer by layer. Because of that `src/` is not runnable as it stands: a `.ts` module has no `.js` twin in the tree, so every check, the CLI entry and the installer use `dist/`.
- A mode is a named assembly list (D35, D43): one TOML per mode, looked up from low to high in the shipped `modes/`, then `~/.ligule/modes/<name>.toml`, then `<project root>/.ligule/modes/<name>.toml`, and the highest hit wins whole — nothing is merged across layers. `run`, `tui` and `host` pick one by `--mode <name>` over the config's `mode`, defaulting to the shipped `minimal`; `tools` and `call` do not read one. The file states both fields (`tools`, `prompt`) even when one is empty, and a field the loader does not act on yet refuses a non-empty value rather than pretending it took effect. A mode names neither skills nor extensions nor MCP servers: those live in the registry, and a mode can only narrow what the registry already holds (D46). Disclosure entries sit outside that field — a mode cannot select `skill` by name and cannot hide it (D63), so naming one in a mode file fails with `mode_tool_not_selectable` and `kernel.selectable()` is what the narrowing step is limited to. Switching is one protocol call (`mode.set`): the Host loads the name immediately so a broken list fails at the request, applies it at once when no round runs and otherwise when the current round ends, and naming the mode already in use withdraws a pending switch. `applyMode` hands back the undo for its own narrowing, and the record gets a `mode` event only when the list handed to the model differs from the last one recorded — attaching a client that only reads must not write (D41, D65).
- An extension is one ESM file whose default export is a function; the host calls it with a frozen object that has exactly four members — `registerTool`, `registerPrompt`, `onEvent`, `request` (D37, D69). Nothing else is handed out, not even which extension this is. Sources are the user's install directory (`~/.ligule/extensions/*.js`, sorted) plus paths written in the user layer or the command line; a project or local layer entry is refused with `extension_source_ignored` because a repository does not decide what code this process runs (D68). One extension failing to load undoes only its own registrations and produces a diagnostic with its path; the round continues, and an event handler that throws is contained the same way (`extension_handler_failed`). `request()` goes through `kernel.call`, so the decision chain, argument validation and the session record apply exactly as they do to a model call. Modes now select prompt fragments by name (`prompt = [...]` or `"*"`); an unknown name fails at load with `mode_prompt_unavailable` instead of quietly dropping the slot. Extensions load only when a session is really built — `tools`, `call` and the read-only `ligule extensions` command import no code.
- Skills are discovered from four fixed directories, in this order: `<project root>/.ligule/skills/`, `<project root>/.agents/skills/`, `~/.ligule/skills/`, `~/.agents/skills/` (D45, D57). A directory holding `SKILL.md` is one skill root and is not searched deeper; a repeated name keeps the highest one and names the ignored path in a diagnostic. The model is offered one tool, `skill`, with the actions `search`, `activate` and `read` (D50) — `read` is bounded to that skill's own directory, which is a second boundary next to the workspace one. Names and descriptions are inlined into the system prompt while they fit the metadata budget and replaced by a fixed sentence telling the model to search when they do not (D55); `activate` refuses to hand over instructions whose `metadata.ligule-requires` names a capability this run does not offer, and loading a skill never registers a tool nor loosens a decision (D51, D56). Nothing on disk means neither the tool nor the prompt fragment: an unusable row in the table would change the prefix bytes of every request (D12). `ligule skills` is the read-only way to see what this directory would load and why any skill was dropped; the protocol does not grow a method for it and the prompt carries only a count (D64).
- Prompt templates live in two directories — `<project root>/.ligule/prompts/` and `~/.ligule/prompts/`, the project one winning — and are found recursively, because the relative path *is* the command name (`git/release/prepare.md` is `/git:release:prepare`, D45); there is no `name` field that could drift away from it. Expansion happens only in the Host (D54): `$ARGUMENTS` and `$1`–`$9`, arguments split on shell quoting, an unbalanced quote refused with `template_arguments_unbalanced`, and both placeholder forms replaced in one pass so a `$1` inside an argument is never expanded a second time. The one user event keeps the expanded `text` plus `raw`, `arguments`, `source` and `digest` — `session.modelView()` reads `text`, so the provenance fields never reach the model (I5) — and every client draws `raw`. A line whose first word has the shape of a command is an invocation, so an unknown name is refused with `template_unknown` naming what is loaded rather than handed to the model unexpanded.
- `fetch` is a first-party optional tool (D48): the registry holds it, `minimal` hides it and `full` offers it. It reads the URL only as GET over http(s) with no cookies, no custom headers and no credential this machine already has, and the target is judged by the address it resolves to, not the string: addresses are classified from their bytes, so `::ffff:127.0.0.1` and its normalised `::ffff:7f00:1` are the same loopback, and `::`, `0.0.0.0` and multicast land in a reserved class rather than defaulting to public. The decision chain refuses link-local, metadata endpoints and reserved addresses outright, forces a question for loopback and private ranges, and lets public ones through the normal order (D58). Resolution happens once and the socket is bound to the approved address while the hostname stays in the `Host` header, the TLS SNI and certificate verification — approving one address and connecting to another is the second half of the same hole. Every redirect is rebuilt, re-resolved, re-classified and re-judged, and only a same-origin hop continues: a changed host or port raises `fetch_redirect_denied`, because a public URL is not permission to reach an internal one.
- MCP is stdio only, over the official TypeScript SDK (D52, D60, D70): a server is `command` plus `args` in the config, `command` carries no arguments (a value with whitespace that is not a file on disk raises `mcp_command_invalid`), and `env` values must be exactly `${NAME}` — a literal credential in a config file is refused, and a variable that is not set is left unset rather than passed through as text. The model sees two fixed tools, `mcp.inspect` and `mcp.call`, both disclosure entries outside what a mode can select (D63), and neither is registered when no server is configured. `mcp.call` asks two questions before calling: did you read *this* version (`mcp_not_disclosed`), and is the version you read still what the server offers (`mcp_definition_stale`)? Every definition lookup re-runs `tools/list`, because caching a definition would hide a server that changed underneath. Arguments travel as one JSON string — the controlled schema subset (D14) has no "arbitrary nested object" — and the host validates them against the declaration the server sent. What the chain, the guards and the approval prompt see is the effective capability `mcp:<server>/<tool>`, never `mcp.call`; MCP's own `readOnlyHint`/`destructiveHint` annotations are untrusted input and cannot grant a pass. Closing a server kills its process tree (the SDK's `close()` alone left a test child alive for ~90s).
- `subagent` is a first-party plugin tool rather than a kernel concept (D61, D71): the derived agent runs a second loop in the same process over its own kernel and its own session record, and the decision chain it gets is the parent's instance — a derived agent can never sit at a looser level than the run that spawned it. Only one level exists, because the child's assembly is the parent's plugin list, which has no `subagent` in it. Its record is a branch file next to the parent's, named `<parent id>.sub-<n>.jsonl`, so reading one session reads its branches. Two model-visible parameters (`task`, plus an optional `mode` naming the list the child runs under — `mode_unknown` when no layer holds that name, `subagent_mode_paths_required` when this run has no mode directories); what comes back into the parent's context is the child's text, its session id and the record path. v1 runs one child at a time (the concurrency field is untouched, D29), and the tool registers only when a session is really built, so `ligule tools` still counts nine. Reading one of those branch files needs no new protocol method (D74): `session.read` takes any id whose record sits in the session directory, whether or not a kernel holds it right now, and an id that is not a plain file name is refused with `session_id_invalid` before anything touches the directory. The terminal opens one with `/sub <seq>` over the parent's delegation result and labels whose sequence numbers are on screen; the desktop entry is a panel in the slot registry, so the render trunk never names branches.
- `src/host/` is the client protocol and its carrier (D30): `protocol.js` names the operations and their argument shapes in the same schema subset the kernel validates, `connection.js` moves one message per line, `host.js` owns the sessions and reaches the loop only through what a host may inject anyway — the provider, the decision chain's ask channel, and the session log. A new carrier adds a file next to `connection.js` and changes neither the table nor the kernel. The session authority stays in the Host: a client that disconnects loses nothing, and a second process opens the same record. The approval the Host sends out carries the shell backend and the executable that would run a command line (D67), so the person answering sees which grammar judged the text; a call with no command text carries neither field, which keeps the request the same shape over both carriers.
- `src/tui/` is the second client of the same protocol (D33): it starts a Host in its own process and connects the two ends with the in-memory carrier (`src/host/memory.js`), so it reads frames exactly like the desktop shell does. It imports `host/` and React/Ink only — never a kernel private interface. `ink` and `react` are optionalDependencies: `ligule tui` reports `tui_dependency_missing` when they are absent, and every other command works without them. Ink throws rather than degrades when stdin cannot do raw mode, so `App` takes an `interactive` flag and the command refuses a non-terminal earlier with `tui_terminal_required`. Committed rows live in `Static`, which never repaints them, so the two in-app commands work around that instead of fighting it: `/show <seq>` re-draws one record from the session log into the dynamic area (`seq` is the stable number in the record, not a screen line) and `/mode [name]` sends `mode.set`, whose pending switch shows as `mode:a→b` in the status line (D40, D65). The status line keeps its own prefixes for mode and policy and drops `tools:` first when the terminal is too narrow.
- `desktop/` is the Tauri shell: a Rust side that opens the window, spawns the Node host and moves one line per frame in each direction, plus a `frontend/` built by Vite (React + TypeScript, `npm run build` → `dist/`, which is what Tauri embeds). Rust names no protocol method, event or error code, and `desktop/src-tauri/Cargo.toml` carries no serialization, HTTP or WebSocket dependency — the shell does not read what it forwards. UI content mounts through `desktop/frontend/src/slots.ts`: a status pill or a dock panel registers into a declared slot instead of editing the render path. `src/main.tsx` reads the transport from `window.__LIGULE_TRANSPORT__` when a page sets one, which is how the browser check drives it without a shell. `desktop/` sits outside `package.json#files`, so it never enters the tarball.
- The installer carries its own runtime (D34): `node desktop/fetch-runtime.mjs` vendors a pinned `node.exe` plus the built `dist/` tree (it refuses when `dist/cli.js` is missing) and its production dependencies into `desktop/vendor/` (never committed), and `bundle.resources` mounts them as `node/` and `app/`. The shell then looks for the backend in this order — `LIGULE_DESKTOP_CLI`, the bundled `app/dist/cli.js`, then `dist/cli.js` walking up from the executable — and prefers the bundled node over `NODE` and `PATH`. A native dependency that is not installed is skipped by the vendoring step on purpose: the kernel already degrades when a parser or a search backend is missing.
- A session record is an append-only JSONL log whose first line is not an event: `{kind: 'session', formatVersion, sessionId, projectRoot, createdAt, mode?}` (D73). Reading fails closed — a `formatVersion` newer than this build raises `session_version_unsupported`, a header line anywhere but the first raises `session_header_position`, and an event kind this build never writes raises `session_event_unsupported` unless the record marks it `ignorable`, which is the only way to add an informational kind without breaking older readers. A record that predates the header is read as version 0 and is never retrofitted with one. The header carries no sequence number, so events still start at 0, and a reopened log numbers on from the last sequence it read — that is what stops a crash's half-line from producing two events with the same number.
- `ligule sessions` reads the record directory and lists past runs without building a kernel, loading an extension or opening a session (D73): the first line gives the project and the start time, the last `mode` event gives the list it ran under, and a dispatched call with no result is counted so a half-finished session is visible from the listing. `--json` is for scripts, `--project <root>` filters by that first line — a record whose project cannot be read is not this project's. `ligule resume <id> <text>` takes the mode from the last one that took effect in that record and compares its digest (D78): same name same digest continues, a changed file on disk refuses with `resume_mode_changed` naming both digests, and `--mode` always wins — quietly falling back to the shipped `minimal` would decide the tool surface for someone who already chose one. Measured on this machine: scanning 100/1000/5000 records takes 25/204/1080 ms (whole-file reads, linear), which is why there is no index yet.
- Reopening a record through the writable path (`session.open`) closes its open tail: every assistant turn carrying a call with no result gets one appended — `kind: 'tool'`, `failed`, code `tool_outcome_unknown`, the call id and arguments, plus a `recovery` field naming the turn it repairs — so the next request body stays valid and the model reads the same fact the host did. Scanning again adds nothing, which is the whole idempotence argument; reading (`session.read`, the listing, the UI) reports the gap and never writes. A tool may declare `readOnly` — kernel-side only, never model-visible, no effect on the decision chain (I3) — and that one bit chooses the sentence: read-only says run it again if needed, everything else says look at the current state first, because the measured behaviour on Windows is that an `exec` child outlives a hard-killed host and lands its effect afterwards (D72, D79).
- Every failure carries a stable code (`KernelError#code`). A tool that did not finish raises `KernelError`; a failure of the kernel itself — the session log cannot be written, spilled content cannot be stored — raises `KernelRuntimeError`. The loop continues past the first and stops on the second. An error a tool raises without a code is wrapped into `tool_failed`, the original goes into `cause`, and the failure is recorded so the model sees it. A code alone is not something the model can act on, so every failure a tool can return also carries `detail` — one sentence naming what to do next; the code is for the host, the content is for the model, and the CLI prints both. Every call the model asked for ends up answered in the log, including one the loop decided not to run (`tool_skipped`): an unanswered call makes every later request body invalid, and that state never heals itself.
- Tool parameter schemas use a supported subset: at the root `type` (`object`), `properties`, `required`, `description`; on a leaf `type` (`string`, `integer`, `number`, `boolean`), `description`, `minimum`, `maximum`. Registration rejects anything else and names every violation; the kernel validates arguments before the decision chain runs. A full external JSON Schema needs an adapter layer that reduces it to this subset.
- Dependencies install from the lockfile (`npm ci` in both workflows). `scripts/check-pack.js` hands the consumer directory only the transitive closure of `dependencies` — it walks the installed manifests and refuses when a declared runtime dependency is not there — so a devDependency can never be what makes the unpacked package work. Copying the whole `node_modules` would hide exactly the failure this check exists to catch: a tarball that is short at runtime. The first devDependency (`@modelcontextprotocol/server-filesystem`, the test MCP server) is present and stays out of the consumer.
- `tree-sitter`, `tree-sitter-bash` and `tree-sitter-pwsh` are native addons, but all three tarballs ship prebuilds for six platform and architecture combinations, so no compiler is involved and npm blocking their install script does not matter. The bash grammar is loaded lazily through `createRequire`; the PowerShell one is an ESM graph with a top-level await, so `require` refuses it and only a dynamic `import` works — and its `main` names a directory without an extension, so it is imported by its `bindings/node/index.js` location. A parser that cannot load drops the decision chain to asking every time and says so in the reason, instead of failing at startup; `scripts/check-pack.js` parses one command line with each grammar through the installed package, because a missing native addon would otherwise look like "this machine asks a lot".
- `exec` runs under the shell backend the host chose (D59): the config key `exec.shell` takes `auto`, `bash` or `powershell`, and `auto` probes the platform — on Windows PowerShell first (`pwsh` before the built-in `powershell`), Git Bash next if neither is on `PATH`; on POSIX, bash (`/bin/bash`, then `bash` on `PATH`, then `sh`). Probing touches no process: known locations are stat-ed directly and bare names are looked up directory by directory through `PATH`. Naming one backend that this machine does not have raises `exec_shell_unavailable` and lists what was searched — running the other grammar instead would execute text the chain never read. The kernel resolves the backend once per call and hands the same object to the decision chain and to the tool, and the tool record carries `{kind, executable, segments}` so a transcript shows which grammar judged the line and which binary ran it. PowerShell is parsed with a deliberately small subset (D66): a literal command with literal arguments only — `|`, sub-expressions, script blocks, splatting, the invocation operator, redirects, comments, reserved declaration forms, a non-ASCII or `$`/backtick-bearing argument and any parse error all fall back to asking. Two platform facts the shape depends on (measured on Windows 11 with Windows PowerShell 5.1, 2026-10-04): `-Command` returns 1 for any failing native command — the real code stays in `$LASTEXITCODE` — and quoted arguments passed to a native command lose `<` and `>`, which is why the exec tests run a temporary script file rather than `node -e`. The tail `; exit $LASTEXITCODE` is therefore *not* appended to every PowerShell command: a failing cmdlet leaves `$LASTEXITCODE` alone, so appending it turns a failure into the previous native command's code, usually 0 (`Get-Process -Name nope` answers 1 without the tail and 0 with it). The kernel appends it only when the chain read the whole line as one simple command *and* that command name is an executable on `PATH` or a known location (tried with each `PATHEXT` extension); `withNativeExitCode` decides, the record carries the tail when one was applied, and a call path with no decision chain gets no tail at all. Prefer the missing code over the masked failure.
- Tools read configuration from the frozen snapshot the kernel passes them and log through the injected three-method interface (`debug` and `log` required, `error` optional). Nothing under `src/` writes to an output sink directly, and a host that injects no logger gets no output. The project layer can come from a repository someone else wrote, so a `__proto__` key in any layer is refused (`config_key_unsafe`) rather than assigned onto the prototype, and only plain tables merge recursively — a TOML datetime is a class instance and counts as a value, so a higher layer replaces it instead of merging into an empty table.
- The runtime floor is a single value written in four places: `engines.node` here, the README badge and `PRIMARY_NODE_VERSION` in each workflow. `test/runtime-version.test.js` asserts they agree, and the workflows install Node from that variable instead of repeating a number per step.
- `packages/rg-*` hold no committed binaries: `npm run build-rg` downloads the ripgrep version pinned in `scripts/ripgrep-pin.json`, checks size and sha256, and writes the executable plus its license texts there. The declaration itself waits for the publish: an unpublished name cannot enter the lockfile, and `npm ci` refuses a package.json that is not fully covered by it (first CI run on 2026-10-02 failed exactly there). Until then the two entries stay out of optionalDependencies, search falls back to walking the tree, and the two comparison tests skip. `ci.yml` runs `npm run build-rg` before `npm test`, so the two tests comparing the real backend against our own walk run on both matrix platforms instead of skipping; the download branch of that script has not yet run anywhere, first result is the next CI log. Nothing resolves `rg` from `PATH`: a bare `ripgrepPath` in config resolves as a relative path and fails.
- Release: bump `package.json` and `VERSION` together, then tag `vX.Y.Z` on `main`. The tag drives the publish workflow, which runs `npm run build-rg` and publishes the two ripgrep platform packages before the main one. `test/runtime-version.test.js` keeps all three versions equal to the release version.
- The very first publish cannot use npm Trusted Publishing: npm requires the package to exist before a trusted publisher can be bound to it. Publish `0.0.1` with a token, then configure the trusted publisher and let the workflow take over.
- The npm account has 2FA enabled, so a direct `npm publish` asks for a one-time password; run it interactively or pass `--otp`. Tokens that bypass 2FA are being restricted by npm for direct publishing, so do not reach for one. Trusted Publishing (OIDC) is not affected by 2FA — another reason to move publishing to the tag-driven workflow as soon as the package exists.

## Verify

```sh
npm test
npm run check-pack
```

`npm run check-pack` packs the tarball, unpacks it, checks every entry `package.json` points at, then imports the unpacked package from an empty consumer directory; it refuses before packing when `dist/` is missing, so run `npm run build` (or `npm test`, which builds) first. `npm test` exercises the same `dist/` the package ships, so it cannot see a file left out of the `files` list or an `exports` entry the tarball does not carry — that is what this check is for. Invoke the script through npm: on Windows Node refuses to launch `npm.cmd` without a shell, so the script needs `npm_execpath`.

`npm test` reports `skipped 2` when no ripgrep has been built locally: those two compare the real backend with our own tree walk and cannot be faked. Run `npm run build-rg` first when a change touches either backend.

`testplace/real-round.mjs` drives one round against the configured endpoint (`~/.ligule/config.toml` plus `LIGULE_API_KEY`) and prints the session record afterwards; it is the entry for the two acceptances a local server cannot cover — a real request whose tool call is assembled from stream fragments, and the CLI printing a real round. That directory is neither committed nor published, and the script holds no credential of its own.

The shell has its own checks, outside `npm test` because they need a compiler and a window: `cd desktop/src-tauri && cargo test` covers locating the backend entry and moving frames through the child's pipes, `testplace/check-desktop-window.ps1` starts the built shell, counts the host processes it spawns, screenshots the window and asserts that killing the shell leaves no orphan, and `testplace/serve-frontend.mjs` plus `testplace/check-desktop-frontend.mjs` render rows, approvals and panels in a browser against an in-page fake host — the window check cannot type when the shell fails to take foreground focus.

The terminal client is checked in `test/tui.test.js`: the row projection is a pure function with four cases, and one case paints the component onto a fake stdout. Those skip when `ink` or `react` is missing, the same way the two ripgrep comparisons do. To look at the layout, run `node testplace/render-tui.mjs`; to use it for real, `ligule tui` in a terminal.
