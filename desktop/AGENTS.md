# Desktop

Rules for `desktop/`: the Tauri shell and its Vite frontend (D34). The repository-wide rules in [../AGENTS.md](../AGENTS.md) apply here too; this file states what only this directory has to keep.

- `desktop/` is the Tauri shell. Rust opens the window, starts the Node host and moves one line per frame each way. `frontend/` is a Vite project (React, TypeScript) built by `npm run build` into `dist/`, and Tauri embeds that directory.
- Rust names no protocol method, event or error code, and `desktop/src-tauri/Cargo.toml` carries no serialization, HTTP or WebSocket dependency.
- The shell has five commands: `host_send`, `host_stop`, `host_restart`, `app_quit`, `default_workspace`. `host_restart` runs the same start path, which hands back the previous child and terminates it, so only one process ever writes frames into the window. Which session to take back is the interface's decision, carried by `session.open` (D30). `default_workspace` names the directory a first session belongs to while no workspace exists yet — the system documents directory, with `ligule/default-workspace` created inside it — and it reads no protocol frame and starts no process.
- Interface content registers into a declared slot in `desktop/frontend/src/slots.ts` instead of editing the render path. `src/main.tsx` reads `window.__LIGULE_TRANSPORT__` when a page sets one, which is how the browser check drives it without a shell.
- The desktop transcript holds only the pages it read: the first `session.read` asks for the newest page, and 「显示更早」 asks for the page before that cursor. The whole record stays on the Host side.
- Only the rows inside the viewport are in the DOM (`react-virtuoso`). A prepended page shifts the viewport's first index by the number of rows added, so the row being read stays where it was.
- The desktop rail reads those two fields: a name becomes that row's title, an archived session sinks below its group and dims — it is not hidden, so it stays openable and un-archivable. The desktop writes no label yet; the naming entry there belongs with the dialog work.
- The display tier chooses which kinds of row enter that list (`shownIn`), rather than hiding rows with CSS: the viewport measures every row it is given, and a row hidden by style measures as nothing (D90, U48).
- Every transcript row carries the sequence number of the record event it was projected from, so a search hit names a row that exists; rows the interface writes itself carry none.
- The row at the top of the viewport is remembered per session, by that sequence number. Opening that session again lands there when the row is inside the page in hand; otherwise the view stays at the end — reading pages or widening the display tier just to restore a position is not done, and a position that cannot land writes nothing to the transcript.
- A page that arrives after the person switched away is dropped: it changes neither the rows nor the cursor, so an older answer cannot land in another session's transcript (方案 6.2).
- The rail's search box asks `sessions.search` once the typing settles (300 ms) and re-asks on Enter, which is also the retry handle when the answer fails. A 「只看这一份」 chip names the record that session is writing, and that read reaches the spilled files. A hit opens its session and lands on its row: that read walks back pages until the event is in hand, and hands the rows and the landing target over in one batch, because a `scrollToIndex` issued in the frame after the data grows loses to the viewport sticking at its last row. Landing remounts the viewport at that row (D97 scale aside, this is the `react-virtuoso` mount-time position) and marks that row for 2.5 s.
- A hit whose row the display tier filters out raises the tier to `detailed` and lands; a hit with no row at all — a `label` — says so in the transcript instead of waiting for a jump that never comes.
- The composer behaves like the terminal's: a sentence typed while a round runs joins that session's queue (UI state, never the record) and shows in a band above the input with 收回 per item and 全部收回 for the band; the send button reads 排到后面 there. Cancelling pauses the band, and 继续 is a separate press. Items are keyed per session, so another session's queue neither shows nor sends here (方案 5.2).
- Which session a running round belongs to is interface state, and there can be more than one at a time: the composer, the 取消 handle, the 「这一轮结束」 row, the draft that comes back after a lost request and `status.get`'s answer all belong to that round's own session, so a background session finishing neither sends another session's queued sentence nor paints in this one's transcript. The top bar says how many *other* sessions are running, and the rail marks a session that is running or that ended a round while it was not being looked at (方案 3.1、5.2).
- The rail can list a second project directory, typed into its own box and kept in `projects` inside `ligule.ui` — the interface's storage, never the configuration file, so it enters no model context and no project business config (D90). That list is capped by nothing: it says what this window wants to see, and the durable roster is the registry in the data root (方案 5.5.1). A session's record, lock and tool directory follow the root that session names on `session.open` or `session.create`; roots are compared by workspace identity, so the same directory spelled differently is one project (方案 3.2, D110).
- Grouping reads the record's two fields: `workspaceOrigin` of `explicit` puts a session in its workspace's group above, and anything else — `default`, or a record that predates the fields — is listed below without a group (方案 5.5.4). Placement never comes from comparing a path to the current default directory. One group folds behind a button carrying `aria-expanded`; folding is this window's display state and drops nothing. The rule is `groupByWorkspace` in `src/rail.ts`, and `dev/rail.check.mjs` is its check.
- Each load reads that roster through `workspaces.list`, so a group's title and directory come from the registered row — display name last written there, path last registered — rather than from what this window happens to have typed. The roster is read before the listings and every row in it is one of the directories asked (`visibleRoots`), together with what this window watches: a workspace the terminal client registered is listed, grouped and searched from here too, because the durable roster — not this window's own list — decides what is findable (方案 5.5.1、5.5.3, 审阅 F3). A search that runs while the listing is still being read waits for it, so both ask one set of directories. A read that fails says so in the rail's own notice and still lists every session under the directory the record carries. The chip on each group row is the registry's `default` field in button form: pressing it writes `workspace.default.set` and re-reads, so the rail shows what the host stored, and pressing it while pressed sends a blank directory to clear the selection.
- `session.create` names no project root unless the person chose one: `createCallOf` (方案 5.5.3) takes the chosen workspace as `explicit`, otherwise the project the session in view belongs to, otherwise the registered default, all three reported as `default`. With no registered default the desktop asks its own shell for one (`default_workspace`), registers what that returns and creates the session there; when that handoff fails the transcript says why with the code it got and no session is created. The desktop never treats the Host process's inherited working directory as its own workspace.
- `desktop/frontend/src/hotkeys.ts` is that surface's binding table in the same shape as the terminal's: an action id, its default key spec, the view it lands in (window, composer, candidate list), and one sentence. `actionOf(event, view)` decides what a press does, and the palette notes, button titles, the composer placeholder and the 快捷键 panel are built from the same table instead of naming a key twice (方案 6.1). Cmd and Ctrl are one modifier here, because the shell runs on Windows and the carrier reports both. Personal overrides live in the `keys` table of `ligule.ui` and the settings dialog's 键位 section edits them: the next key pressed becomes that action's key, Esc cancels the capture, and while a capture is open the window layer takes no global key at all. A rebinding that would land two actions in one view is refused and named, and never reaches storage.
- The same `@` rule reaches the other surface: `desktop/frontend/src/mentions.ts` holds the two judgements the terminal's `commands.ts` holds, and the band above the input draws the Host's answer with an 插入 button per row. Its project line names the root that answer carried rather than the one the interface remembers, since a session that has not read its record header knows no root.
- The draft and the queued sentences are saved under the same `ligule.ui` key in two tables keyed by the project root the record header names, then by session id (D90, 方案 5.1). A session that has nothing left to keep drops out of both tables instead of leaving an empty row; a save that the machine's storage refuses says so once in the transcript, because the text is still on screen and must not read as saved.
- The input history is not kept here: the walk reads `history.read` and a send appends that one sentence with `history.append`, so this surface and the terminal client walk the same list (方案 5.5.6). Drafts and queues stay per session in this window's own storage — only the history crosses surfaces. A write that does not land leaves the sentence walkable in this window and says nothing more, because the send itself does not wait on it.
- While an input method is composing, Enter commits the candidate, arrows walk the candidates and Esc cancels the word — so those three reach no interface action: no send, no history walk, no panel close, no cancelled round. The check reads `isComposing` and the keyCode 229 that browsers keep after `compositionend`, in one place (`hotkeys.ts`) that both the composer and the window layer call (方案 5.1, 5.4).
- The approval card's expandable body derives the same three fields in `desktop/frontend/src/rows.ts` (`changeOf`, `changeBody`) from the same rule the terminal follows, so the summary line and the `-`/`+` blocks cannot disagree. Its header names the project that call will touch: `approval.request` carries that root with the ask, so a card for a session that is not the one on screen names its own project rather than none (方案 5.4). The tier line reads the ask's own `policy`, `policySource` and `policyForced`: a background card explains the tier that asked, never the one the session on screen runs.
- The 模型与端点 and 审批规则 panels read and write the project the session on screen belongs to: `config.get` and `config.set` carry that root, so the value, the version and the save follow the project being looked at rather than the one the Host was launched on (方案 3.2).
- Answering an approval moves focus off the button that took the press, since Enter on a focused button presses it again — one way a decision can land that nobody made. A round that ends with its own session still holding unanswered asks adds a row saying how many and that they settled as 不允许; before that the column simply went quiet, which read as though nothing had been asked.
- A question card belongs to the session that asked: 取消这一轮 cancels that session's own round and pauses that session's queue, never the round on screen, since the card may be showing a background session (审阅 F1). When that round ends, the Host is replaced or the person cancels it, that session's cards go away — one the Host no longer waits on would sit in front of another session's ask and read as still answerable — and each card's questions with whatever was typed stay in the transcript as one row (`questionEcho`) — filed under that session and appended when the person opens it if that round ended off screen — because an answer is delivered once and an unsubmitted one must not vanish (D107, 方案 R1).
- Reconnecting after the Host was killed waits out the dead writer's lease instead of failing. That lease expires within ten seconds (`SESSION_LOCK_STALE_MS`), so a 重连 pressed inside those ten seconds would otherwise hear 那份会话接不上：session_locked with the banner still up. The interface retries the open once a second for up to twelve seconds and only then leaves the failure on screen, and the in-flight flag clears on every path so one failed press cannot block the next. `session.acquire` itself still answers `session_locked` at once: two live windows reaching for one record should hear that immediately rather than after a wait.
- Only a `turn` event whose status is `completed` becomes a row, and that row is the one carrying 「从这里分支」; the number it hands over is that event's own `seq`, the same one the rows were stamped with. The palette's 「分支这一份会话」 sends no `at`, which is the whole-record copy. Both entries then land on the new session and tell the rail to re-read the directory, because that record is the one the Host just wrote (方案 4.3).
- The 导出全文 panel opens the machine's own save dialog and sends the chosen destination to `session.export`: the page reads no record and writes no file, and the shell grants only `dialog:allow-save` for it (方案 6A). Opened in a plain browser that dialog cannot appear, so the panel says the failure and picks no destination instead. A same-prefix branch file already sitting at its computed name is not overwritten — that target is reported in the panel next to the branches whose record could not be read.
- `desktop/frontend/package.json` is the frontend's own list and never joins the npm package. `react-virtuoso`, `radix-ui` and `lucide-react` are pinned exactly: the first costs about 61 kB in the bundle (19 kB gzipped), `radix-ui` 1.7.0 about 93 kB (30 kB gzipped), `lucide-react` 1.53.0 about 5 kB (2 kB gzipped) because only the shapes in use survive tree-shaking. `@tauri-apps/plugin-dialog` 2.8.1 is the frontend half of the save dialog and is the only Tauri plugin the window may use.
- The installer type is written per platform: `tauri.windows.conf.json` asks for NSIS, `tauri.linux.conf.json` for AppImage and the Debian package, `tauri.macos.conf.json` for the DMG, and the bundler merges that file into `tauri.conf.json` with arrays replaced whole. `bundle.targets` has only the two shapes 「all」 or one list, so one shared list naming all four would ask a Windows runner to build a Linux package. The `desktop` job in `ci.yml` runs the four rows of `RELEASE.md` as a matrix, each on a runner of its own architecture; it builds, checks what it is about to ship and uploads the files as attachments, and installs none of them.
- `desktop/` stays outside `package.json#files`.
- The installer carries its own runtime (D34). `node desktop/fetch-runtime.mjs` vendors the pinned Node, the built `dist/` tree, production dependencies and installed transitive optional dependencies into `desktop/vendor/`. The Node archive is chosen by `<platform>-<arch>`, defaulting to the machine running the script, and `desktop/node-pin.json` holds one file name and one SHA-256 per target — four targets, matching the rows in `RELEASE.md`, which `test/runtime-version.test.js` compares. POSIX extraction takes `bin/node` and lays it down as `node/node` with the executable bit set, Windows takes `node.exe`, and both carry Node's own `LICENSE` beside the binary. `desktop/vendor/node/.vendored` names the target and version that were fetched, so a leftover from another target cannot pass as ready. This includes platform native packages when installed and omits unrelated root optional dependencies such as the terminal UI packages. That directory is never committed, and `bundle.resources` mounts them as `node/` and `app/`. A runtime tree built on one platform must not be shipped for another: the native bindings inside it are the host's own, which is why each target's installer is built on a runner of that platform.
- The shell looks for the backend in this order: `LIGULE_DESKTOP_CLI`, the bundled `app/dist/cli.js`, then `dist/cli.js` walking up from the executable. It prefers the bundled node over `NODE` and `PATH`.
